Reviewed against the complete CV-Controlled Endless Runner problem statement.
Baseline: `7967c3cb08af729033f189acc648c234a969615d` on `main`.

The required features are implemented. Software checks pass after the fixes
below. **Full empirical sign-off is still pending:** the repository does not

## Issues reproduced and fixed

1. **A crouched preparation suppressed a genuine jump.** Once the classifier
   entered `DUCKING`, any loss of foot contact cancelled the action, so a natural
   countermovement jump could never trigger `JUMP`. A short gap after duck release
   also blocked a real takeoff until neutral rearming. Both failures were
   reproduced before editing the implementation.
   - A 200 ms confirmation window now permits a crouch-to-flight transition using
     the existing bilateral heel/toe clearance, upward hip velocity and 35 ms
     debounce gates. A verified takeoff is also allowed within 200 ms of duck
     release; another crouch still requires stable neutral rearming.
   - Grounded standing-up, single-foot steps, short spikes, occlusion and an
     unconfirmed return to contact do not become jumps.
   - A single `JUMP` event releases the virtual duck before applying the jump
     impulse. The recorder captures the new jump and its preparation/takeoff
     samples without falsely completing an interrupted crouch.
   - A sufficiently long preparatory crouch can already have issued `DUCK_START`.
     The controller cannot know future movement intent from a grounded squat.

2. **Live metrics from the preceding action leaked into the next action.** A
   crouch could display the previous flight time/height/hip rise; a jump could
   display the previous bottom pause. New actions now clear unrelated values and
   timestamps. The explicitly labeled completed-action history is retained.

3. **The README overstated completion.** The unconditional production-ready
   heading and unmeasured desktop planning-number tables have been replaced with
   explicit measured evidence and remaining validation work. Historical
   maintainer-reported functional testing is attributed rather than presented as
   a new measurement.

## Evidence needed before claiming complete validation

1. Run the updated desktop app on the submission machine and verify physical
   controls, especially crouch-to-jump, held duck, landing, occlusion and restart.
2. Follow the [manual protocol](ASSIGNMENT_AUDIT.md#manual-detection-and-metrics-protocol):
   two participants, slow/ordinary/brisk jumps and crouches, plus neutral/sway and
   recovery negatives. Fill `manual-validation.csv` with actual misses, false
   triggers and repeated events. These are observations, not estimated counts.
3. After warm-up, reset the performance sample and run three 60 s trials with
   accepted jumps and duck/release actions. Enter CPU/GPU/RAM, OS, camera and
   participant code, then export session JSON for each trial. Report averages,
   duration, action counts, resolution, model and capture-timestamp source.
4. Document threshold/EMA/frame-rate uncertainty and the equal-COM-height
   assumption of ballistic height. Quantified angle/flight accuracy requires
   paired reference measurements; do not infer it from successful gameplay.
5. Optionally record a short physical-control demo. Label any simulated input.

The committed old software-WebGL benchmark has no accepted actions, so its
action latency is correctly unavailable. It cannot satisfy the missing physical
performance evidence.
